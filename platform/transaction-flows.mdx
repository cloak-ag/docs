## Canonical data shape

Both `Transact` and `TransactSwap` use:

- `proof_bytes`: 256-byte Groth16 proof
- `public_inputs`: 264-byte packed blob

Public input layout:

- `root[32]`
- `publicAmount[8]` (signed LE)
- `extDataHash[32]`
- `mintAddress[32]`
- `nullifiers[64]`
- `commitments[64]`
- `chainNoteHash[32]`

## Keys the flows use

Every flow works with two values the wallet derives from its spend key:

- **The wallet's UTXO keypair** (`ownerUtxoKeypair`). It owns every note the wallet creates for
  itself: deposits, change, consolidation merges and swap refunds. Spending any of them needs its
  private key.
- **The viewing key `nk`**. It encrypts the chain note each transaction carries and derives the
  per-note blinding that lets a scan rebuild a commitment. **`nk` is view-only: it can find and read
  your notes, never spend them or sign for funds.**

The SDK never takes the owner of a new note from an input note, and never infers `nk` from a note's
own key: the spend flows require `ownerUtxoKeypair`, and every flow that writes a chain note needs
the wallet's `nk` (explicit, or derived from `ownerUtxoKeypair`).

## Deposit flow (`publicAmount > 0`)

1. SDK creates output UTXOs, owned by the wallet's UTXO keypair, and generates proof inputs.
2. SDK resolves Merkle data from chain.
3. Transaction is submitted (direct signer path for deposit variants).
4. Program verifies proof and appends commitments to the tree.
5. SDK resolves commitment index and persists local proof context.

## Withdraw/transfer flow

1. SDK builds 2-in/2-out witness and computes nullifiers. Change is owned by the wallet's UTXO
   keypair. For a private transfer, change is output 1, which the circuit binds to input 0's key, so
   the SDK puts a wallet-owned input first and, if there is none, moves the inputs into one
   wallet-owned note in a preceding shielded transaction.
2. SDK optionally ensures viewing-key registration.
3. SDK submits the proof + public inputs and the resulting on-chain transaction lands.
4. Program rejects reused nullifiers and enforces amount/fee constraints.
5. Client polls transaction status until completed or failed.

## Swap flow

1. SDK generates proof for withdraw-like step with swap params.
2. `TransactSwap` (Tx1) opens `SwapState`.
3. Settlement path (Tx2) executes the swap and validates output min amount.
4. Status includes `swap_phase`, signatures, and error context.
5. Timeout/close paths can reclaim state if settlement cannot complete. The returned principal lands
   as a refund note owned by the wallet's UTXO keypair, with a blinding derived from `nk` and the
   swap's first input nullifier.

## Reliability behaviors

- Stale root retries: SDK regenerates proofs when root history moved, on a bounded retry budget
- Nullifier preflight: `preflightNullifiers` throws `UtxoAlreadySpentError` before a spend, in one batched RPC call
- Settlement confirmation: `confirmTransactSettlement` decides from chain state whether a submission landed by polling input-nullifier PDAs; a verdict of `unknown` means the SDK could not check and is never success
- Direct-submission gating: `assertDirectSubmissionLanded` throws `SettlementVerificationError` unless nullifier PDAs prove the transaction was applied, because a confirmed-looking status field is not proof
- Swap refund recovery: `discoverSwapRefunds(connection, programId, nk, { ownerUtxoKeypair })` finds a stranded swap refund from key material, and the wallet spends it with its own keypair through the ordinary `transact()` path. Discovery is forward-looking only: it finds refunds whose blinding was derived from the wallet's `nk`, so an empty result is not proof that no stranded refund exists
- Older notes: scans flag notes built by earlier SDK releases with `legacyExposed: true`. They are found and spendable; move them into a note owned by the wallet's UTXO keypair by spending them to yourself
- Pending-deposit recovery: `loadPendingDeposits` and `cleanupStalePendingOperations` persist in-flight deposits so a crash or navigation away does not strand a note. Browser storage is used by default and the records carry spending secrets, so encrypt that storage in production
