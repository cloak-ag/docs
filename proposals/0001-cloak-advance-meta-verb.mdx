# CIP-0001: `cloak_advance` — generic shielded meta-verb

> **Status:** draft / pre-implementation. Not on the v1 critical path.
> Captured to inform Cloak v2 program ABI before we lock another set
> of instructions.

## Motivation

Shield-pool v1 has two near-identical Groth16-verifying entrypoints:

| Discriminator | Name             | Purpose                               |
|--------------:|------------------|----------------------------------------|
| `0`           | `Transact`       | deposit, withdraw, shielded transfer   |
| `1`           | `TransactSwap`   | shielded → external Jupiter swap       |

Both run the same nullifier / commitment / root-history / proof-verify
sequence. They diverge only in what they do *after* verifying the
proof:

- `Transact` either credits/debits the pool's lamport balance or no-ops
  (pure shielded transfer).
- `TransactSwap` opens a `SwapState` PDA, then `PrepareSwapSol` and
  `ExecuteSwap` follow up via the relay worker.

Every additional shielded action we want to support (shielded → Drift
deposit, shielded → Kamino lend, shielded → SPL token swap, shielded
→ Marinade stake, etc.) currently requires:

1. New instruction discriminator on `shield-pool`.
2. New circuit constraints — or worse, a new circuit + trusted setup.
3. New SDK encoder + new audit surface.

This is the same N-endpoint problem
[winterwallet](https://github.com/blueshift-gg/winterwallet) solved
with a single **`Advance`** verb at
`program/src/instructions/advance.rs:62-204`. Adapting that pattern to
Cloak gives us composability with arbitrary Solana programs — and the
*next* shielded-DeFi venue ships as an SDK update with zero on-chain
program redeploy.

## Proposal

Replace `Transact` + `TransactSwap` (and ahead-of-time replace any
future shielded action) with a single instruction:

```
discriminator: u8 = 0x10  // tentative; reserve range 0x10-0x1F for v2
cloak_advance:
  proof:           [u8; 256]      // Groth16 proof
  public_inputs:   [u8; 264]      // root, publicAmount, extDataHash,
                                  // mintAddress, in_nullifiers,
                                  // out_commitments, chainNoteHash
  inner_payload:   varlen         // count-prefixed list of inner ixs
                                  // (see § Inner Payload)
```

After verifying the Groth16 proof and applying the standard nullifier
+ commitment side-effects, the program walks the `inner_payload` and
performs each inner instruction via `invoke_signed` with the relevant
shield-pool PDA promoted to signer.

This is pattern-identical to winterwallet's `Advance` flow:

1. **Snapshot state:** read current pool balance / merkle root /
   relevant PDA into local variables.
2. **Apply commitments + nullifiers eagerly** (write before CPI to
   prevent re-entry from spending the same nullifier).
3. **Verify proof** against the snapshotted state.
4. **CPI loop** with the pool PDA promoted to signer for any inner
   account whose pubkey matches the pool address.
5. **Strict exhaustion check:** all inner accounts consumed, payload
   buffer empty.

### Inner payload wire format

Match winterwallet exactly:

```
inner_payload =
    num_instructions:u8
 || (num_accounts:u8 || data_len:u16 LE || data:bytes)^num_instructions
```

Account ordering for the outer transaction:

```
[shield_pool_pda, treasury_pda, merkle_tree_pda, nullifier_pdas...,
 commitment_pdas..., prog_0, acc_0_0, acc_0_1, ..., prog_1, acc_1_0, ...]
```

The fixed prefix (pool, treasury, merkle, nullifiers, commitments) is
the existing `Transact` account list. The trailing accounts are the
"passthrough" set — programs and metas the user wants to invoke.

### Account-meta promotion

For each inner instruction's account list, any account whose pubkey
equals the shield-pool's withdrawal-authority PDA gets `is_signer =
true` flipped on. This is what lets the inner CPI authenticate as the
pool — Jupiter, Drift, Kamino, etc. see a signer and proceed. The
off-chain encoder must scrub `is_signer = false` on every passthrough
meta so the only source of signer-ness is the on-chain promotion.
(See winterwallet `client/src/instruction.rs:184-194` and
`sdk/ts/src/instructions/advance.ts:152-156`.)

### Bounds

```rust
pub const MAX_PASSTHROUGH_ACCOUNTS: usize = 96;       // tx-size limit
pub const MAX_CPI_INSTRUCTION_ACCOUNTS: usize = 16;
pub const MAX_INNER_INSTRUCTIONS: usize = 8;
```

Tighter than winterwallet (128/16) because we already pay for ~10
fixed pool/treasury/nullifier/commitment accounts in every advance,
and the proof + 264-byte public input eat ~600 bytes of the 1232-byte
legacy-tx budget.

## Privacy implications

This is the part that's **not** identical to winterwallet. Winterwallet
binds *every* trailing account address into the Winternitz signature
preimage, so a swapped account → signature failure. We need an
analogous binding in the Groth16 public input set.

Two options:

### Option 1: Bind inner-account addresses into `extDataHash`

Extend the existing `extDataHash` (already a 32-byte commit-to-out-of-
circuit-data hash) to include:

```
extDataHash = poseidon_or_sha256(
    existing_ext_data,
    inner_payload_bytes,
    sorted_inner_account_addresses,
)
```

The circuit constraint is unchanged — it just hashes a longer
`ext_data` blob. The SDK encoder produces the canonical bytes; the
program recomputes them and rejects on mismatch. Cheap; reuses the
existing public input slot.

**Trade-off:** the *count* of passthrough accounts becomes a metadata
side channel (the `extDataHash` blob length is observable via tx size).
Mitigated by padding to fixed quantiles (8/16/32 inner accounts).

### Option 2: New circuit constraint over inner payload

Add an explicit `innerPayloadHash[32]` to the public input layout (for
a total of 296 bytes). Circuit constrains it but doesn't constrain its
contents — same role as `chainNoteHash`. SDK + program must agree on
the hash function (Poseidon vs SHA-256 — Poseidon is ZK-friendly but
adds rows; SHA-256 is what we use elsewhere).

**Trade-off:** circuit re-spec → trusted setup re-run → ceremony cost.
Probably not worth it for the marginal cleanliness vs Option 1.

**Recommendation:** Option 1. Reuse `extDataHash`. No circuit changes.

## Composability examples

### Shielded → Jupiter swap (replaces `TransactSwap` + `ExecuteSwap`)

```ts
const inner = [jupiterSwapIx({ pool: poolPda, ... })];
const advance = await encodeCloakAdvance({
  proof, publicInputs, innerInstructions: inner,
});
const tx = new Transaction().add(advance);
```

The pool PDA appears in `jupiterSwapIx`'s account list as a non-signer;
the program flips it to signer at CPI time. No `SwapState` PDA, no
two-step settlement, no relay worker for the swap path.

### Shielded → Drift deposit

```ts
const inner = [drift.deposit({ user: poolPda, amount, ... })];
// same wrapping
```

Drift sees the pool PDA as a signer. User's funds enter Drift while
their identity remains private (only the pool authored the action).

### Shielded → SPL transfer (no external venue)

```ts
const inner = [
  splToken.transfer({ source: poolTokenAccount, destination: recipient, ... }),
];
```

Replaces today's `Transact` withdraw path with a more general one. The
`publicAmount` field still gates value conservation in the circuit;
the inner CPI just expresses *where* the value goes.

## What does NOT change

- The Groth16 transaction circuit (with Option 1).
- The 2-in/2-out commitment topology.
- The 32-level merkle tree.
- The 100-deep root history ring.
- Nullifier PDA derivation (`["nullifier", pool, hash]`).
- Pool / treasury / merkle PDA seeds.
- `chainNoteHash` semantics.
- Fee math (`FIXED_FEE_LAMPORTS + gross * 3 / 1000`).

## What's removed

- Disc `1` `TransactSwap`.
- Disc `3` `PrepareSwapSol` (subsumed by inner CPI to Jupiter).
- Disc `4` `ExecuteSwap` (likewise).
- Disc `5` `CloseSwapState` (no `SwapState` PDA to close).
- The relay worker's swap settlement path.

## Migration

`Transact` (disc `0`) stays for one full release as a deprecated
alias; SDK emits a deprecation warning. Relay infra and existing tx
history readers continue to work.

After 1 release of dual support, `Transact` is removed and `disc 0`
returns `InvalidInstructionData`.

## Risks + open questions

1. **Tx-size pressure.** 256-byte proof + 264-byte public input + the
   wallet/treasury/merkle/nullifier/commitment account fixed prefix
   already eats ~700 bytes. Inner payload + passthrough account list
   has ~500 bytes to work in. Real-world Jupiter routes can blow this
   out → forces v0/ALT transactions for non-trivial swaps. The TS SDK
   already supports v0 estimation (port from winterwallet
   `sdk/ts/src/transaction.ts:190-254`), but we'd need to commit to
   v0-only for `cloak_advance`. Reasonable; mainline Solana tooling
   has supported ALTs for two years.

2. **Re-entry hardening.** Cloak's nullifier creation is per-PDA
   (`["nullifier", pool, hash]`), so a re-entrant CPI cannot re-spend
   the same nullifier (PDA already exists → `init_if_needed` fails).
   Equivalent protection to winterwallet's "advance the root before
   CPI" pattern, but free — we should still document the invariant in
   the program comments.

3. **Risk-oracle integration.** `Transact` deposits today require
   risk-oracle quote accounts on certain configurations. Under
   `cloak_advance`, the deposit case is just `inner = []` with
   positive `publicAmount`; the risk-oracle accounts move into the
   fixed account prefix, conditioned on a config flag. No conceptual
   change, but the encoder needs awareness.

4. **Audit surface.** The CPI dispatch loop is a new attack surface.
   Winterwallet's version is ~80 LOC of Pinocchio with `MaybeUninit`
   stack arrays for zero-alloc; we mirror that. Independent audit on
   the dispatch logic before mainnet.

5. **Trusted setup.** Option 1 (reuse `extDataHash`) avoids a re-run.
   If we ever choose Option 2, we plan it as a coordinated v3 ceremony
   with adequate participants.
