This page tracks the current public exports of `@cloak.dev/sdk`.

## UTXO API

The UTXO free functions are the primary entrypoint. There is no client class to construct.

```typescript
transact(params, options)
transfer(inputUtxos, recipientPubkey, amount, options)
partialWithdraw(inputUtxos, recipient, withdrawAmount, options)
fullWithdraw(inputUtxos, recipient, options)
swapUtxo(params, options)
swapWithChange(inputUtxos, swapAmount, outputMint, recipientAta, minOutputAmount, options, recipientWallet?)
```

`transact` is the single engine entrypoint and the sign of `externalAmount` classifies the
flow: positive shields (deposit), negative withdraws, zero is a shielded transfer.
`transfer`, `partialWithdraw` and `fullWithdraw` are shaped wrappers over it.

Every one of these takes a `TransactOptions` object. `connection`, `programId` and `relayUrl`
are required on all flows; supply either `depositorKeypair` (programmatic) or the wallet
callbacks `signTransaction` / `signMessage` plus `walletPublicKey` (browser). `relayUrl` has
no default and is not read from the environment, so pass it explicitly on every call. Every flow
except a deposit needs an authenticated sender and throws before proof generation without one:
see [Request authentication](/sdk/request-authentication).

<Note>
The signatures below are those of 0.2.6, in which `nk` is view-only. 0.2.5 accepted the earlier
shapes (positional `createRecoverableDepositUtxo`, no `ownerUtxoKeypair`), and they throw on 0.2.6.
</Note>

**Two keys, two jobs.** Every flow works with two values derived from the wallet's seed:

- `ownerUtxoKeypair`, the wallet's long-lived UTXO keypair (`deriveUtxoKeypairFromSpendKey(skSpend)`).
  It **owns** every note the wallet creates for itself: deposits, change, consolidation merges and
  swap refunds. Only its private key can spend them.
- `nk`, the viewing key (`getNkFromUtxoPrivateKey(ownerUtxoKeypair.privateKey)`). **`nk` is
  view-only: it can find and read your notes, never spend them or sign for funds.** It encrypts the
  chain notes and derives the per-note blinding a scan uses to rebuild a commitment.

`transfer`, `partialWithdraw`, `fullWithdraw`, `swapUtxo` and `swapWithChange` take `SpendOptions`,
which is `TransactOptions` with `ownerUtxoKeypair` required:

```typescript
type SpendOptions = TransactOptions & { ownerUtxoKeypair: UtxoKeypair };
```

The owner is never inherited from `inputUtxos[0]`. Each flow validates the keypair (non-zero private
key, public key derived from it) and throws before touching the network if it is missing. When
`chainNoteViewingKeyNk` / `getChainNoteViewingKeyNk` is not given, the flow uses the canonical `nk`
of `ownerUtxoKeypair`.

`transact` keeps `ownerUtxoKeypair` optional, but it no longer infers `nk` from a note's own key.
It needs the wallet's `nk` (explicit, or the canonical `nk` of `ownerUtxoKeypair`) whenever it writes
a chain note or registers the viewing key, which is every call unless both `disableChainNotes` and
`enforceViewingKeyRegistration: false` are set. It throws `transact requires the wallet's viewing
key` otherwise.

`transfer` places the recipient's note at output 0 and change at output 1, and the circuit requires a
non-zero output 1 to be owned by the key of input 0. So `transfer` puts a wallet-owned input first.
When none of the inputs is owned by `ownerUtxoKeypair` and there is change, it first moves the
inputs into one note owned by the wallet keypair (an extra shielded transaction, reported through
`onProgress`) and then sends from that note. That extra step cannot run inside a single
`transactBatch` item, so a batched transfer from such inputs throws instead.

UTXO primitives:

```typescript
generateUtxoKeypair()
createUtxo(amount, keypair, mint?)
createZeroUtxo(mint?)
computeUtxoCommitment(utxo)
computeUtxoNullifier(utxo)
selectUtxos(available: Utxo[], targetAmount: bigint): Utxo[] | null
verifyUtxos(utxos, connection, programId, commitment?)
serializeUtxo(utxo: Utxo): Uint8Array
deserializeUtxo(bytes: Uint8Array): Promise<Utxo>
```

`selectUtxos` needs two checks at every call site, not one. It returns `null` instead of throwing
when the available notes do not cover the target, so a truthy check is the whole insufficient-balance
path. And it knows nothing about the circuit's two-input cap: it will happily return three notes for
a large target, and `transact` then throws `Maximum 2 input UTXOs allowed` before proving. Check the
length as well as the null. `partialWithdraw` and `fullWithdraw` consolidate down to two inputs for
you; `transfer` does not, so cap the selection yourself.

That consolidation is not free, and it is worth budgeting for. `partialWithdraw` merges the two
smallest notes at a time, so `n` inputs cost `n - 2` shielded transactions before the withdrawal
itself, each one separately proved, signed and submitted. `fullWithdraw` delegates to it and behaves
the same. In a browser that is `n - 2` extra wallet approvals, and `options.onProgress` is the only
thing that reports them: it fires `Consolidating notes (n remaining)...` on each round. Each merge
also creates a fresh intermediate note that the SDK never hands back, and its blinding is fresh
randomness held only in that process, so a run that dies between a merge and the final withdrawal
strands that note on-chain permanently, exactly as the change-note warning below describes. Prefer
two inputs where you can, and treat a many-input withdrawal as a long resumable operation rather
than a single call.

`serializeUtxo` / `deserializeUtxo` are a fixed 128-byte encoding of one note: amount, private key,
blinding, mint and leaf index. That is the full spending secret in a byte array, so treat the output
as key material and encrypt it at rest. `deserializeUtxo` is async because it re-derives the public
key and recomputes `commitment`. One edge to know: a note at leaf index `0` comes back with `index`
undefined, because the encoding cannot tell index `0` from unset.

Note storage and key material. The SDK persists nothing on its own; these are the pieces you build a
store out of, and the full pattern is
[Where your notes live between sessions](/sdk/wallet-integration#where-your-notes-live-between-sessions).

```typescript
UtxoWallet
LocalStorageAdapter
MemoryStorageAdapter
importWalletKeys(keysJson: string)
exportWalletKeys(keys: CloakKeyPair)
expandSpendKey(skSpend: Uint8Array): ExpandedSpendKey
getNkFromUtxoPrivateKey(utxoPrivateKey: bigint): Uint8Array
```

- [`UtxoWallet`](/sdk/wallet-integration#where-your-notes-live-between-sessions) is the live note set:
  `Utxo` objects per mint, spent flags, balance, stats and input selection. It does not persist
  itself. `serialize()` and the static `UtxoWallet.deserialize(json)` give you a JSON string that
  handles the `bigint` fields; where that string goes is your choice. It drops `commitment`, so
  recompute with `computeUtxoCommitment` after restoring, or `verifyUtxos` reports every restored
  note as `skipped` rather than spent or unspent.
- [`LocalStorageAdapter`](/sdk/wallet-integration#where-your-notes-live-between-sessions) implements
  `StorageAdapter` over browser `localStorage`, holding `CloakNote` records and wallet keys under the
  keys `cloak_notes` and `cloak_wallet_keys` by default.
- [`MemoryStorageAdapter`](/sdk/wallet-integration#where-your-notes-live-between-sessions) is the same
  interface held in process. It persists nothing and loses everything on reload: use it for tests, or
  when storage lives entirely on your side.
- `importWalletKeys` / `exportWalletKeys` move a `CloakKeyPair` in and out of a JSON string.
- `expandSpendKey` derives `(ask, nsk, ovk)` from a spend key; `getNkFromUtxoPrivateKey` returns the
  32-byte `nk` for the wallet's UTXO private key. `nk` is the incoming viewing base: it decrypts
  chain notes and is what the recovery helpers below scan with. It is view-only and never derives a
  key that can spend.

The two halves do not connect. `UtxoWallet` does not take a `StorageAdapter`, and a `StorageAdapter`
does not store `Utxo` objects. The note set is the half that decides solvency.

<Warning>
Do not build sends with `UtxoWallet.prepareSend` or with `SimpleWallet`, even though both are
exported. `prepareSend` derives the recipient output from a freshly generated random keypair rather
than from the recipient's key, so the note it produces is unspendable by the recipient and by you.
`SimpleWallet.sync()` throws `Sync not yet implemented`. Use `transfer`, which builds the recipient
output from the Cloak pubkey you pass it. The rest of `UtxoWallet` is sound: `addUtxo`, `markSpent`,
`getBalance`, `getUnspentUtxos`, `getStats`, `selectInputs`, `serialize` and `deserialize`.
</Warning>

Note helpers, all free functions:

```typescript
parseNote(jsonString)
serializeNote(note, pretty?)
encodeNoteSimple(note)
exportNote(note, pretty?)

```

## Result types

Every UTXO flow resolves to a `TransactResult`:

```typescript
interface TransactResult {
  signature: string;
  inputNullifiers: bigint[];
  outputCommitments: bigint[];
  newRoot: string;
  commitmentIndices: [number, number];
  siblingCommitments: [bigint, bigint];
  preTransactionLeftSibling?: bigint;
  outputUtxos: Utxo[];
  viewingKeyRegistered?: boolean;
  merkleTree?: MerkleTree;
  addressLookupTableAccounts?: AddressLookupTableAccount[];
}
```

`swapUtxo` and `swapWithChange` both resolve to a `UtxoSwapResult`, which extends it:

```typescript
interface UtxoSwapResult extends TransactResult {
  swapStatePda: string;
  nullifier: string;
  requestId?: string;
  refund: {
    publicKey: string;     // the wallet's UTXO public key (ownerUtxoKeypair)
    blinding: string;
    derivedFromNk: boolean; // always true: the blinding is derived from nk and the swap's nullifier
  };
}
```

`refund` describes the note that returns the swap input to the pool if the swap times out before
its second transaction lands. It is owned by `ownerUtxoKeypair`, so you spend it with the wallet's
own keypair; the private key is deliberately not repeated in the result. Persisting `refund` is the
fast path; `discoverSwapRefunds` finds the same note again from key material if you lose it.

## Recovery helpers

These exports let a wallet rebuild its notes from key material, with no local note store. Matching
always needs the wallet's UTXO public key, because every note is owned by `ownerUtxoKeypair`; `nk`
alone only finds the note, and spending it always needs the owner's private key.

```typescript
createRecoverableDepositUtxo({ amount, viewingKeyNk, ownerUtxoKeypair, mintAddress?, noteSalt? })
createRecoverableChangeUtxo(amount, ownerUtxoKeypair, viewingKeyNk, mintAddress?, noteSalt?, outputIndex?)
matchDepositNote({ viewingKeyNk, noteSalt, amount, mintAddress, outputCommitments, ownerUtxoKeypair? })
matchChangeNote({ viewingKeyNk, noteSalt, amount, keypair, mintAddress, outputIndex, outputCommitments, ownerUtxoPublicKey? })
discoverSwapRefunds(connection, programId, viewingKeyNk, { ownerUtxoKeypair, limit?, untilSignature?, batchSize?, onStatus? })
matchSwapRefundLeaf({ viewingKeyNk, inputNullifier, amountAfterFee, commitment, ownerUtxoKeypair? })
deriveSwapRefundAuthorization(viewingKeyNk, inputNullifier, ownerUtxoKeypair)
```

`createRecoverableDepositUtxo` takes one options object and cannot be called without
`ownerUtxoKeypair`. The note it builds is owned by that keypair, and only its blinding is derived
from `(nk, noteSalt)`, which is what lets a later scan rebuild the commitment. It resolves to
`{ utxo, noteSalt }`; pass the same salt to `transact` as `options.chainNoteSalt`, together with
`chainNoteViewingKeyNk` (or `ownerUtxoKeypair`). A salt that never reaches the chain note leaves the
deposit undiscoverable.

`createRecoverableChangeUtxo` is the change-note counterpart, used by `partialWithdraw`, `transfer`
and `swapWithChange` for you. Its owner must be the wallet keypair (it refuses a `privateKey: 0n`
placeholder or a public key that does not match). Call it yourself only when you build outputs for
`transact` directly; `transact` refuses a self-owned output whose blinding is not derivable from the
wallet's `nk` and the transaction's salt.

`discoverSwapRefunds` walks program history for swap timeout-refund leaves that belong to the wallet
and returns them. `ownerUtxoKeypair` is required: pass the real keypair to get spendable results, or
`{ privateKey: 0n, publicKey }` for a view-only scan. It is forward-looking only: a refund whose
blinding was drawn from raw randomness has no derivation to replay, so an empty result is not proof
that a wallet has no stranded refund.

The legacy helpers `deriveLegacyDepositNoteSecrets` and `deriveLegacySwapRefundAuthorization` exist
only so scans keep finding notes built by earlier SDK releases. Never build a new note from them.

### Restore from the Note Index

```typescript
recoverNotesFromIndex({ relayUrl, connection, programId, poolMints, viewingKeyNk, ownerUtxoKeypair, cursor?, legacyViewingKeyNks?, legacyCutoffLeaf?, concurrency?, onProgress?, signal? })
  // -> { notes, atRisk, pending, cursor, stats, warnings }
fetchNoteIndexHead(relayUrl, { signal?, timeoutMs?, maxRetries? })
  // -> { format, epoch, pageSize, watermark, completePages, chainTip }
NoteIndexHeadBehindError // retryable: keep the cursor and try again later
NoteIndexFormatError     // the index did not verify
```

Restores a wallet's notes with one RPC request instead of a chain walk. Usage, the cursor contract
and polling: [Restore notes from the Note Index](/sdk/note-index).

### Notes flagged `legacyExposed`

Every recovered note (`RecoveredDepositNote`, `RecoveredChangeNote`, `RecoveredSwapRefund`, and the
scan records built on them) carries `legacyExposed: boolean`. `true` marks a note built by an earlier
SDK release whose owner key was derived from `nk` rather than from the wallet's spend key. These come
back complete and spendable. Move them under the wallet keypair by spending them to yourself (a
`transfer` to `ownerUtxoKeypair.publicKey`, or a `partialWithdraw` whose change lands under the wallet
keypair), and treat the result as an ordinary note.

<Warning>
Recovery is a backstop, not storage. Persist `result.outputUtxos` before you report success:
[where your notes live between sessions](/sdk/wallet-integration#where-your-notes-live-between-sessions).
A `transfer`'s change sits at output 1, which the chain note does not describe, so a scan recovers its
blinding but not its amount.
</Warning>

## Fee constants

Fees are enforced on-chain from each pool's `PoolConfig`; `transact` reads the live config before
building a fee-bearing proof. These constants mirror the deployed SOL-pool defaults for display
math. SPL pools (USDC/USDT) charge `450_000` base units fixed (0.45) + 0.3%; see
[Fee Model](/protocol/fee-model).

```typescript
FIXED_FEE_LAMPORTS       // 5_000_000
VARIABLE_FEE_NUMERATOR   // 3
VARIABLE_FEE_DENOMINATOR // 1000
VARIABLE_FEE_RATE        // 0.003
MIN_DEPOSIT_LAMPORTS     // 10_000_000
LAMPORTS_PER_SOL         // 1_000_000_000

calculateFee(amountLamports: number)
calculateFeeBigint(amountLamports: bigint)
isWithdrawAmountSufficient(amountLamports: bigint)
getDistributableAmount(amountLamports: number)
formatAmount(lamports: number, decimals?: number)
parseAmount(sol: string)
```

These values cover the native SOL pool. SPL pools (USDC and USDT) charge a fixed 0.45 token,
450,000 raw units at 6 decimals, plus the same 0.3 percent variable fee. The program reads the
effective values from the `pool_config` PDA; the SDK does not compute SPL fees.

## Advanced `TransactOptions`

Five options a standard integration never sets, listed because nothing else documents them.

```typescript
expectedMint?: Address;            // the mint the CALLER believes it is spending
relaySupplementalAlt?: boolean;    // one-signature SPL deposits (default false)
transactionVersion?: 0 | 1;        // message version for SDK-built transactions (default 0)
externalFeePayer?: ExternalFeePayerAdapter; // a payer that covers network fees
relayAuthBatch?: RelayBatchAuthItemHandle;  // set by transactBatch, not by hand
```

**`expectedMint`** — every flow takes the pool from the notes it is handed, so the SDK cannot
otherwise tell a deliberate USDC withdrawal from a SOL withdrawal that was handed a USDC note by
mistake. Both are well-formed and both settle. Set `expectedMint` and the SDK refuses the
transaction when the input notes disagree. Optional for backward compatibility — **pass it on every
flow you can.**

**`relaySupplementalAlt`** — when `true` and `relayUrl` is set, an SPL deposit that needs a
supplemental address lookup table asks for a shared table to be extended instead of creating a
depositor-signed throwaway one, so **the user signs exactly once instead of twice**. Any failure
falls back to the depositor-signed ephemeral-ALT path automatically. Off by default, which preserves
the old behaviour exactly.

**`transactionVersion`** — `0` (default) builds a v0 message with ComputeBudget instructions. `1`
builds a Transaction V1 message (SIMD-0385): 4,096-byte packet, every account static with no lookup
tables, compute budget in the message header. It needs the cluster's v1 gate active *and* a signer
that signs v1 messages — a local key pair does; a browser wallet may not yet.

**`externalFeePayer`** — lets a deposit come from a wallet holding no SOL: the adapter's payer covers
the network fee and on-chain rent and is reimbursed in an SPL token inside the same transaction.

**`relayAuthBatch`** — the handle `transactBatch` passes to each item so the row is authenticated by
the batch's single signature. It takes precedence over `depositorKeypair` and `relayAuthSigner`.
Set it yourself only if you drive the coordinator directly.

## Request authentication and endpoint pinning

Private sends, withdrawals and swaps carry a signed sender. Standard integrations only pass
`signMessage` + `walletPublicKey` (browser) or `depositorKeypair` (server) in `TransactOptions` and
never touch these; they exist for callers driving submission themselves.

```typescript
buildRelayAuthPreimage(endpoint, programId, body, sender, nowSeconds?, fields?): RelayAuthPreimage
canonicalJson(value: unknown): string
explainRelayAuthRejection(responseText: string): string | null
submitTransactToRelay(args: SubmitTransactToRelayArgs)

RelayAuthPreimage; // { sender, auth_issued_at, auth_nonce, message }
RelayAuthSigner; // MessageSigner | TransactionSigner (Kit). Build one from a wallet
                 // adapter with messageSignerFromCallback(address, signMessage).

TRANSACT_AUTH_FIELDS; // 9 fields, sorted; order is part of the agreement
TRANSACT_SWAP_AUTH_FIELDS; // 19 fields, sorted; `slippage_bps` must always be present

REQUEST_AUTH_MAX_AGE_SECONDS; // 300 (285 usable after the SDK's transit margin)
REQUEST_AUTH_MAX_FUTURE_SKEW_SECONDS; // 30

CLOAK_PRODUCTION_RELAY_URL; // name of the production endpoint, never a default
RELAY_ORIGIN_ALLOWLIST; // origins this build may reach; pinned at build time
BUILD_ALLOWS_LOCAL_ENDPOINTS; // derived: true only for a local build
```

`maxWalletApprovals` on `TransactOptions` caps wallet dialogs for one swap (default `5`). Sends and
withdrawals sign exactly once. Full contract: [Request authentication](/sdk/request-authentication).

## Batch signing

`transactBatch` runs N private spends behind **one wallet approval**. Each item is proved
concurrently so every proof exists before the wallet is asked, then all items are submitted under a
single batch signature.

```typescript
transactBatch(
  items: readonly TransactBatchItem[],
  options: TransactBatchOptions,
): Promise<TransactBatchResult>

TransactBatchItem;    // { params: TransactParams; options?: Partial<TransactOptions> }
TransactBatchOptions; // TransactOptions, plus:
                      //   proofConcurrency?  items proved at once (default 2)
                      //   submitConcurrency? items released at once after signing (default 3)
TransactBatchResult;  // { results: TransactBatchItemOutcome[]; approvals: number }
TransactBatchItemOutcome; // { status: "fulfilled"; value: TransactResult }
                          // | { status: "rejected"; reason: unknown }

RELAY_BATCH_AUTH_MAX_ITEMS; // 64 -- hard cap per call
```

`results` has one entry per item in input order, and a rejected item leaves the others unaffected.
`approvals` counts the wallet dialogs actually raised: 1 for the batch, plus 1 per wave of
stale-root re-proves.

The call requires `relayUrl` and an authenticated sender — `depositorKeypair`, or `walletPublicKey`
with `signMessage`, or `signer`. Both are checked before any proof is computed, so a batch that
cannot be authenticated fails without doing work.

<Warning>
**`transactBatch` does not plan the rows.** Two items that spend the same note collide on their
nullifier, and an item that spends another item's change cannot be proved until that change has
landed. Give each item its own already-landed input notes; selecting them is the caller's job.
Above `RELAY_BATCH_AUTH_MAX_ITEMS` the call throws — chunk the payout. The practical bound is
lower than 64, because the chain keeps a ring of 100 recent roots and each item consumes room in
it.
</Warning>
