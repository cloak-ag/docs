This page tracks the current public exports of `@cloak.dev/sdk` 0.2.11. Every name and signature
below is checked against the package's `index.d.ts`.

## UTXO API

The UTXO free functions are the primary entrypoint. There is no client class to construct.

```ts
import {
  fullWithdraw,
  partialWithdraw,
  swapUtxo,
  swapWithChange,
  sweepToWalletKey,
  transact,
  transfer,
  type SpendOptions,
  type SweepResult,
  type TransactOptions,
  type TransactParams,
  type TransactResult,
  type Utxo,
  type UtxoSwapParams,
  type UtxoSwapResult,
} from "@cloak.dev/sdk";
import type { Address } from "@solana/kit";

declare const params: TransactParams;
declare const swapParams: UtxoSwapParams;
declare const options: TransactOptions; // deposits and raw transact calls
declare const spendOptions: SpendOptions; // TransactOptions & { ownerUtxoKeypair: UtxoKeypair }
declare const inputs: Utxo[];
declare const recipient: Address;
declare const recipientCloakPubkey: bigint;
declare const outputMint: Address;
declare const recipientAta: Address;

const a: Promise<TransactResult> = transact(params, options);
const b: Promise<TransactResult> = transfer(inputs, recipientCloakPubkey, 1_000_000n, spendOptions);
const c: Promise<TransactResult> = partialWithdraw(inputs, recipient, 1_000_000n, spendOptions);
const d: Promise<TransactResult> = fullWithdraw(inputs, recipient, spendOptions);
const e: Promise<UtxoSwapResult> = swapUtxo(swapParams, spendOptions);
const f: Promise<UtxoSwapResult> = swapWithChange(
  inputs,
  1_000_000n, // swapAmount
  outputMint,
  recipientAta,
  1n, // minOutputAmount
  spendOptions,
  recipient, // optional recipientWallet
);
const g: Promise<SweepResult> = sweepToWalletKey(inputs, spendOptions);
```

`transact` is the single engine entrypoint and the sign of `externalAmount` classifies the
flow: positive shields (deposit), negative withdraws, zero is a shielded transfer.
`transfer`, `partialWithdraw` and `fullWithdraw` are shaped wrappers over it.
`sweepToWalletKey` moves up to two notes owned by other keys under the wallet's long-lived key with
one self-spend.

`transact` and `transactBatch` take a `TransactOptions` object. Every spend flow (`transfer`,
`partialWithdraw`, `fullWithdraw`, `swapUtxo`, `swapWithChange`, `sweepToWalletKey`) takes
`SpendOptions`, which is `TransactOptions` with `ownerUtxoKeypair` made mandatory. The wallet's `nk`
(`chainNoteViewingKeyNk`) is also required at runtime on every spend, and should be passed on
deposits too. `connection`, `programId` and `relayUrl` are required on all flows. Supply either
`depositorKeypair` (a Kit `KeyPairSigner`, programmatic) or `signer` (the wallet as a Kit
`TransactionSigner`, from `signerFromWalletAdapter`). `signMessage` plus `walletPublicKey` is the
relay-only alternative for sends, withdrawals and swaps. There is no `signTransaction` option.
`relayUrl` has no default and is not read from the environment, so pass `CLOAK_PRODUCTION_RELAY_URL`
explicitly on every call. Every flow except a deposit needs an authenticated sender and throws before
proof generation without one: see [Request authentication](/sdk/request-authentication).

The canonical way to get `ownerUtxoKeypair` and `nk` is from a seed generated once and stored like
a private key. A random key that is lost loses the notes, so do not use `generateUtxoKeypair()` for
anything that holds real funds.

```ts
import {
  CLOAK_PRODUCTION_RELAY_URL,
  CLOAK_PROGRAM_ID,
  createCloakRpc,
  deriveSpendKey,
  deriveUtxoKeypairFromSpendKey,
  generateMasterSeed,
  getNkFromUtxoPrivateKey,
  signerFromSecretKey,
  type SpendOptions,
} from "@cloak.dev/sdk";

const seed = generateMasterSeed().seed; // 32 bytes: generate once, store like a private key
const { sk_spend } = deriveSpendKey(seed);
const ownerUtxoKeypair = await deriveUtxoKeypairFromSpendKey(sk_spend);
const nk = getNkFromUtxoPrivateKey(ownerUtxoKeypair.privateKey); // view-only: finds notes, never spends them

declare const secretKey: Uint8Array;

const spendOptions: SpendOptions = {
  connection: createCloakRpc("https://your-keyed-mainnet-rpc.example"),
  programId: CLOAK_PROGRAM_ID,
  relayUrl: CLOAK_PRODUCTION_RELAY_URL,
  depositorKeypair: await signerFromSecretKey(secretKey),
  ownerUtxoKeypair,
  chainNoteViewingKeyNk: nk,
};
```

UTXO primitives:

```ts
import {
  computeUtxoCommitment,
  computeUtxoNullifier,
  createUtxo,
  createZeroUtxo,
  deserializeUtxo,
  generateUtxoKeypair,
  NATIVE_SOL_MINT,
  selectUtxos,
  serializeUtxo,
  verifyUtxos,
  type Utxo,
  type VerifyUtxosResult,
} from "@cloak.dev/sdk";
import type { Address } from "@solana/kit";

declare const connection: Parameters<typeof verifyUtxos>[1];
declare const programId: Address;
declare const available: Utxo[];

const keypair = await generateUtxoKeypair(); // tests only; derive it from a seed for real funds
const note: Utxo = await createUtxo(1_000_000_000n, keypair, NATIVE_SOL_MINT);
const zero: Utxo = await createZeroUtxo();
const commitment: bigint = await computeUtxoCommitment(note);
const nullifier: bigint = await computeUtxoNullifier(note);
const picked: Utxo[] | null = selectUtxos(available, 500_000_000n);
const state: VerifyUtxosResult = await verifyUtxos([note], connection, programId, "confirmed");
const bytes: Uint8Array = serializeUtxo(note);
const restored: Utxo = await deserializeUtxo(bytes);
console.log(zero, commitment, nullifier, picked, state, restored);
```

`selectUtxos` needs two checks at every call site, not one. It returns `null` instead of throwing
when the available notes do not cover the target, so a truthy check is the whole insufficient-balance
path. And it knows nothing about the circuit's two-input cap: it will happily return three notes for
a large target, and `transact` then throws `Maximum 2 input UTXOs allowed` before proving. Check the
length as well as the null. `partialWithdraw` and `fullWithdraw` consolidate down to two inputs for
you; `transfer` does not, so cap the selection yourself.

That consolidation is not free, and it is worth budgeting for. `partialWithdraw` merges the two
smallest notes at a time, so `n` inputs cost `n - 2` shielded transactions before the withdrawal
itself, each one separately proved, signed and submitted. `fullWithdraw` delegates to it and behaves
the same. In a browser that is `n - 2` extra wallet approvals, and `options.onProgress` is the only
thing that reports them: it fires `Consolidating notes (n remaining)...` on each round. Each merge
also creates an intermediate note that the SDK never hands back. Its blinding is derived from `nk`,
so a run that dies between a merge and the final withdrawal can be recovered by a scan, but only
through the recovery path described below, not by the call itself. Prefer
two inputs where you can, and treat a many-input withdrawal as a long resumable operation rather
than a single call.

`serializeUtxo` / `deserializeUtxo` are a fixed 128-byte encoding of one note: amount, private key,
blinding, mint and leaf index. That is the full spending secret in a byte array, so treat the output
as key material and encrypt it at rest. `deserializeUtxo` is async because it re-derives the public
key and recomputes `commitment`. One edge to know: a note at leaf index `0` comes back with `index`
undefined, because the encoding cannot tell index `0` from unset.

Note storage and key material. The SDK persists nothing on its own; these are the pieces you build a
store out of, and the full pattern is
[Where your notes live between sessions](/sdk/wallet-integration#where-your-notes-live-between-sessions).

```ts
import {
  exportWalletKeys,
  expandSpendKey,
  getNkFromUtxoPrivateKey,
  importWalletKeys,
  LocalStorageAdapter,
  MemoryStorageAdapter,
  UtxoWallet,
  type CloakKeyPair,
  type ExpandedSpendKey,
  type StorageAdapter,
} from "@cloak.dev/sdk";

declare const keys: CloakKeyPair;
declare const skSpend: Uint8Array;
declare const utxoPrivateKey: bigint;

const wallet = new UtxoWallet();
const restored: UtxoWallet = UtxoWallet.deserialize(wallet.serialize());
const browserStore: StorageAdapter = new LocalStorageAdapter();
const testStore: StorageAdapter = new MemoryStorageAdapter();
const json: string = exportWalletKeys(keys);
const back: CloakKeyPair = importWalletKeys(json);
const expanded: ExpandedSpendKey = expandSpendKey(skSpend);
const nk: Uint8Array = getNkFromUtxoPrivateKey(utxoPrivateKey);
console.log(restored, browserStore, testStore, back, expanded, nk);
```

- [`UtxoWallet`](/sdk/wallet-integration#where-your-notes-live-between-sessions) is the live note set:
  `Utxo` objects per mint, spent flags, balance, stats and input selection. It does not persist
  itself. `serialize()` and the static `UtxoWallet.deserialize(json)` give you a JSON string that
  handles the `bigint` fields; where that string goes is your choice. It drops `commitment`, so
  recompute with `computeUtxoCommitment` after restoring, or `verifyUtxos` reports every restored
  note as `skipped` rather than spent or unspent.
- [`LocalStorageAdapter`](/sdk/wallet-integration#where-your-notes-live-between-sessions) implements
  `StorageAdapter` over browser `localStorage`, holding `CloakNote` records and wallet keys under the
  keys `cloak_notes` and `cloak_wallet_keys` by default.
- [`MemoryStorageAdapter`](/sdk/wallet-integration#where-your-notes-live-between-sessions) is the same
  interface held in process. It persists nothing and loses everything on reload: use it for tests, or
  when storage lives entirely on your side.
- `importWalletKeys` / `exportWalletKeys` move a `CloakKeyPair` in and out of a JSON string.
- `expandSpendKey` derives `(ask, nsk, ovk)` from a spend key; `getNkFromUtxoPrivateKey` returns the
  32-byte `nk` for a note's private key. `nk` is the incoming viewing base: it is what decrypts chain
  notes and what the recovery helpers below scan with.

The two halves do not connect. `UtxoWallet` does not take a `StorageAdapter`, and a `StorageAdapter`
does not store `Utxo` objects. The note set is the half that decides solvency.

<Warning>
Do not build sends with `UtxoWallet.prepareSend` or with `SimpleWallet`, even though both are
exported. `prepareSend` derives the recipient output from a freshly generated random keypair rather
than from the recipient's key, so the note it produces is unspendable by the recipient and by you.
`SimpleWallet.sync()` throws `Sync not yet implemented`. Use `transfer`, which builds the recipient
output from the Cloak pubkey you pass it. The rest of `UtxoWallet` is sound: `addUtxo`, `markSpent`,
`getBalance`, `getUnspentUtxos`, `getStats`, `selectInputs`, `serialize` and `deserialize`.
</Warning>

## Result types

Every UTXO flow resolves to a `TransactResult`:

```ts
import type { LookupTable, MerkleTree, Utxo } from "@cloak.dev/sdk";

interface TransactResult {
  signature: string;
  inputNullifiers: bigint[];
  outputCommitments: bigint[];
  newRoot: string;
  commitmentIndices: [number, number];
  siblingCommitments: [bigint, bigint];
  preTransactionLeftSibling?: bigint;
  outputUtxos: Utxo[];
  viewingKeyRegistered?: boolean;
  merkleTree?: MerkleTree;
  addressLookupTableAccounts?: LookupTable[];
}
```

`swapUtxo` and `swapWithChange` both resolve to a `UtxoSwapResult`, which extends it:

```ts
import type { TransactResult } from "@cloak.dev/sdk";

interface UtxoSwapResult extends TransactResult {
  swapStatePda: string;
  nullifier: string;
  requestId?: string;
  refund: {
    publicKey: string;
    blinding: string;
    derivedFromNk: boolean;
  };
}
```

`refund` describes the note the program creates if the swap times out and the input is returned. Its
`publicKey` is the wallet's own `ownerUtxoKeypair` public key, so the private key is deliberately not
repeated here, and its blinding is derived from the wallet's `nk` (`derivedFromNk` is always `true`).
That is what lets `discoverSwapRefunds` find the leaf again from key material if you lose this object.

## Recovery helpers

Two exports let a wallet rebuild notes from key material alone, with no local note store.

```ts
import {
  CLOAK_PROGRAM_ID,
  createCloakRpc,
  createRecoverableDepositUtxo,
  discoverSwapRefunds,
  NATIVE_SOL_MINT,
  type DiscoveredSwapRefund,
  type UtxoKeypair,
} from "@cloak.dev/sdk";

declare const ownerUtxoKeypair: UtxoKeypair;
declare const nk: Uint8Array;

const { utxo, noteSalt } = await createRecoverableDepositUtxo({
  amount: 1_000_000_000n,
  viewingKeyNk: nk,
  ownerUtxoKeypair,
  mintAddress: NATIVE_SOL_MINT,
});

const refunds: DiscoveredSwapRefund[] = await discoverSwapRefunds(
  createCloakRpc("https://your-keyed-mainnet-rpc.example"),
  CLOAK_PROGRAM_ID,
  nk,
  { ownerUtxoKeypair },
);
console.log(utxo, noteSalt, refunds);
```

`createRecoverableDepositUtxo` builds a deposit output owned by `ownerUtxoKeypair`, with a blinding
derived from `(nk, noteSalt)` instead of raw randomness, which is what makes a later cold scan able to
rebuild it. It resolves to `{ utxo, noteSalt }`, and the same salt must reach `transact` as
`options.chainNoteSalt` alongside `options.chainNoteViewingKeyNk` and `options.ownerUtxoKeypair`. A
salt that never reaches the chain note leaves the deposit exactly as undiscoverable as before.

`discoverSwapRefunds` walks program history for swap timeout-refund leaves that belong to the holder
of `viewingKeyNk`. Its options object is required and must carry `ownerUtxoKeypair`: pass the real
keypair for spendable results, or `{ privateKey: 0n, publicKey }` for a view-only scan. It also accepts
`limit`, `untilSignature` and `batchSize`. It finds refunds whose blinding was derived from `nk`, so an
empty result is not proof that a wallet has no stranded refund.

<Warning>
A note built with plain `createUtxo` has a random `blinding` that is written nowhere, so if you lose
it the note is unspendable by anyone, permanently. The spend flows now derive their change from
`nk` (`createRecoverableChangeUtxo`), so a scan can rebuild it, but persist `result.outputUtxos`
before you report success anyway:
[where your notes live between sessions](/sdk/wallet-integration#where-your-notes-live-between-sessions).
Wallet restore from key material alone is `scanTransactions` (history walk) or `recoverNotesFromIndex`
(one bulk feed, one RPC request); both are exported.
</Warning>

## Fee constants

Fees are enforced on-chain from each pool's `PoolConfig`; `transact` reads the live config before
building a fee-bearing proof. These constants mirror the deployed SOL-pool defaults for display
math. SPL pools (USDC/USDT) charge `450_000` base units fixed (0.45) + 0.3%; see
[Fee Model](/protocol/fee-model).

```ts
import {
  calculateFee,
  calculateFeeBigint,
  FIXED_FEE_LAMPORTS, // 5_000_000
  formatAmount,
  getDistributableAmount,
  isWithdrawAmountSufficient,
  LAMPORTS_PER_SOL, // 1_000_000_000
  MIN_DEPOSIT_LAMPORTS, // 10_000_000
  parseAmount,
  VARIABLE_FEE_DENOMINATOR, // 1000
  VARIABLE_FEE_NUMERATOR, // 3
  VARIABLE_FEE_RATE, // 0.003
} from "@cloak.dev/sdk";

const fee: number = calculateFee(1_000_000_000);
const feeBig: bigint = calculateFeeBigint(1_000_000_000n);
const enough: boolean = isWithdrawAmountSufficient(1_000_000_000n);
const net: number = getDistributableAmount(1_000_000_000);
const label: string = formatAmount(1_000_000_000, 4);
const lamports: number = parseAmount("1.5");
console.log(
  fee, feeBig, enough, net, label, lamports,
  FIXED_FEE_LAMPORTS, VARIABLE_FEE_NUMERATOR, VARIABLE_FEE_DENOMINATOR,
  VARIABLE_FEE_RATE, MIN_DEPOSIT_LAMPORTS, LAMPORTS_PER_SOL,
);
```

These values cover the native SOL pool. SPL pools (USDC and USDT) charge a fixed 0.45 token,
450,000 raw units at 6 decimals, plus the same 0.3 percent variable fee. The program reads the
effective values from the `pool_config` PDA; the SDK does not compute SPL fees.

## Advanced `TransactOptions`

Five options a standard integration never sets, listed because nothing else documents them.

```ts
import type {
  ExternalFeePayerAdapter,
  RelayBatchAuthItemHandle,
  TransactOptions,
} from "@cloak.dev/sdk";
import type { Address } from "@solana/kit";

// These five fields are declared on TransactOptions; this interface restates them.
interface AdvancedTransactOptions {
  expectedMint?: Address; // the mint the CALLER believes it is spending
  relaySupplementalAlt?: boolean; // one-signature SPL deposits (default false)
  transactionVersion?: 0 | 1; // message version for SDK-built transactions (default 0)
  externalFeePayer?: ExternalFeePayerAdapter; // a payer that covers network fees
  relayAuthBatch?: RelayBatchAuthItemHandle; // set by transactBatch, not by hand
}

// Compile-time proof that the restatement matches the package.
const check: AdvancedTransactOptions = {} satisfies Pick<
  TransactOptions,
  keyof AdvancedTransactOptions
>;
console.log(check);
```

**`expectedMint`** — every flow takes the pool from the notes it is handed, so the SDK cannot
otherwise tell a deliberate USDC withdrawal from a SOL withdrawal that was handed a USDC note by
mistake. Both are well-formed and both settle. Set `expectedMint` and the SDK refuses the
transaction when the input notes disagree. Optional for backward compatibility — **pass it on every
flow you can.**

**`relaySupplementalAlt`** — when `true` and `relayUrl` is set, an SPL deposit that needs a
supplemental address lookup table asks for a shared table to be extended instead of creating a
depositor-signed throwaway one, so **the user signs exactly once instead of twice**. Any failure
falls back to the depositor-signed ephemeral-ALT path automatically. Off by default, which preserves
the old behaviour exactly.

**`transactionVersion`** — `0` (default) builds a v0 message with ComputeBudget instructions. `1`
builds a Transaction V1 message (SIMD-0385): 4,096-byte packet, every account static with no lookup
tables, compute budget in the message header. It needs the cluster's v1 gate active *and* a signer
that signs v1 messages — a local key pair does; a browser wallet may not yet.

**`externalFeePayer`** — lets a deposit come from a wallet holding no SOL: the adapter's payer covers
the network fee and on-chain rent and is reimbursed in an SPL token inside the same transaction.

**`relayAuthBatch`** — the handle `transactBatch` passes to each item so the row is authenticated by
the batch's single signature. It takes precedence over `depositorKeypair` and `relayAuthSigner`.
Set it yourself only if you drive the coordinator directly.

## Request authentication and endpoint pinning

Private sends, withdrawals and swaps carry a signed sender. Standard integrations only pass `signer`
(browser) or `depositorKeypair` (server) in `TransactOptions` and never touch these; they exist for
callers driving submission themselves.

```ts
import {
  buildRelayAuthPreimage,
  BUILD_ALLOWS_LOCAL_ENDPOINTS, // derived: true only for a local build
  canonicalJson,
  CLOAK_PRODUCTION_RELAY_URL, // the production endpoint, never a default
  CLOAK_PROGRAM_ID,
  explainRelayAuthRejection,
  messageSignerFromCallback,
  RELAY_ORIGIN_ALLOWLIST, // origins this build may reach; pinned at build time
  REQUEST_AUTH_MAX_AGE_SECONDS, // 300 (285 usable after the SDK's transit margin)
  REQUEST_AUTH_MAX_FUTURE_SKEW_SECONDS, // 30
  submitTransactToRelay,
  TRANSACT_AUTH_FIELDS, // 9 fields, sorted; order is part of the agreement
  TRANSACT_SWAP_AUTH_FIELDS, // 19 fields, sorted; `slippage_bps` must always be present
  type RelayAuthPreimage,
  type RelayAuthSigner,
  type SubmitTransactToRelayArgs,
} from "@cloak.dev/sdk";
import type { Address } from "@solana/kit";

declare const sender: Address;
declare const walletSignMessage: (message: Uint8Array) => Promise<Uint8Array>;
declare const requestBody: Record<string, unknown>;
declare const settlement: SubmitTransactToRelayArgs["settlement"];

// A message signer built from a wallet adapter's signMessage.
const relayAuthSigner: RelayAuthSigner = messageSignerFromCallback(sender, walletSignMessage);

const endpoint = `${CLOAK_PRODUCTION_RELAY_URL}/transact`;
const preimage: RelayAuthPreimage = buildRelayAuthPreimage(
  endpoint,
  CLOAK_PROGRAM_ID,
  requestBody,
  sender,
  undefined, // nowSeconds
  TRANSACT_AUTH_FIELDS,
);
// preimage is { sender, auth_issued_at, auth_nonce, message }

const args: SubmitTransactToRelayArgs = {
  relayUrl: CLOAK_PRODUCTION_RELAY_URL,
  requestBody,
  programId: CLOAK_PROGRAM_ID,
  relayAuthSigner,
  settlement, // the on-chain check used to confirm a reported success
  canRetryStaleRoot: true, // true while you still have a re-prove budget
};
const result = await submitTransactToRelay(args);

console.log(
  canonicalJson(requestBody),
  explainRelayAuthRejection("rejected response text"),
  TRANSACT_SWAP_AUTH_FIELDS,
  REQUEST_AUTH_MAX_AGE_SECONDS,
  REQUEST_AUTH_MAX_FUTURE_SKEW_SECONDS,
  RELAY_ORIGIN_ALLOWLIST,
  BUILD_ALLOWS_LOCAL_ENDPOINTS,
  preimage,
  result,
);
```

`maxWalletApprovals` on `TransactOptions` caps wallet dialogs for one swap (default `5`). Sends and
withdrawals sign exactly once. Full contract: [Request authentication](/sdk/request-authentication).

## Batch signing

`transactBatch` runs N private spends behind **one wallet approval**. Each item is proved
concurrently so every proof exists before the wallet is asked, then all items are submitted under a
single batch signature.

```ts
import {
  RELAY_BATCH_AUTH_MAX_ITEMS, // 64: hard cap per call
  transactBatch,
  type TransactOptions,
  type TransactParams,
  type TransactResult,
} from "@cloak.dev/sdk";

interface TransactBatchItem {
  params: TransactParams;
  options?: Partial<TransactOptions>; // per-item overrides
}

interface TransactBatchOptions extends Omit<TransactOptions, "relayAuthBatch"> {
  proofConcurrency?: number; // items proved at once (default 2)
  submitConcurrency?: number; // items released at once after signing (default 3)
}

type TransactBatchItemOutcome =
  | { status: "fulfilled"; value: TransactResult }
  | { status: "rejected"; reason: unknown };

interface TransactBatchResult {
  results: TransactBatchItemOutcome[];
  approvals: number;
}

declare const items: readonly TransactBatchItem[];
declare const batchOptions: TransactBatchOptions;

const outcome: TransactBatchResult = await transactBatch(items, batchOptions);
console.log(outcome.approvals, RELAY_BATCH_AUTH_MAX_ITEMS);
```

`results` has one entry per item in input order, and a rejected item leaves the others unaffected.
`approvals` counts the wallet dialogs actually raised: 1 for the batch, plus 1 per wave of
stale-root re-proves.

The call requires `relayUrl` and an authenticated sender: `depositorKeypair`, or `signer`, or
`walletPublicKey` with `signMessage`. Both are checked before any proof is computed, so a batch that
cannot be authenticated fails without doing work.

<Warning>
**`transactBatch` does not plan the rows.** Two items that spend the same note collide on their
nullifier, and an item that spends another item's change cannot be proved until that change has
landed. Give each item its own already-landed input notes; selecting them is the caller's job.
Above `RELAY_BATCH_AUTH_MAX_ITEMS` the call throws — chunk the payout. The practical bound is
lower than 64, because the chain keeps a ring of 100 recent roots and each item consumes room in
it.
</Warning>

## Solana Kit runtime

Since 0.2.5 the SDK is built on `@solana/kit`. These are the helpers a normal integration touches.

```ts
import {
  address,
  addressFromPublicKey, // web3.js PublicKey -> Address
  confirmSignature,
  createCloakRpc, // pass the result as `connection`
  fetchLatestBlockhash,
  generateKeyPairSigner,
  isAddress,
  sendInstructions,
  sendRawTransaction,
  signerFromKeypair,
  signerFromSecretKey,
  signerFromWalletAdapter, // browser wallet-adapter bridge
  toAddress,
  type Address,
  type CloakRpc, // Rpc<SolanaRpcApi> & { readonly endpoint: string }
  type KeyPairSigner,
  type LegacyWalletAdapter,
  type WalletAdapterBridgeOptions,
} from "@cloak.dev/sdk";

declare const secretKey: Uint8Array;
declare const wallet: LegacyWalletAdapter;
declare const bridgeOptions: WalletAdapterBridgeOptions;
declare const publicKey: { toBase58(): string };
declare const wire: Uint8Array;

const rpc: CloakRpc = createCloakRpc("https://your-keyed-mainnet-rpc.example");
const a: Address = address("11111111111111111111111111111111");
const b: Address = toAddress(a);
const c: Address = addressFromPublicKey(publicKey);
const valid: boolean = isAddress("not an address");

const throwaway: KeyPairSigner = await generateKeyPairSigner();
const fromBytes: KeyPairSigner = await signerFromSecretKey(secretKey);
const fromKeypair: KeyPairSigner = await signerFromKeypair({ secretKey });
const walletSigner = signerFromWalletAdapter(wallet, bridgeOptions);

const blockhash = await fetchLatestBlockhash(rpc);
const signature: string = await sendRawTransaction(rpc, wire);
await confirmSignature(rpc, signature);
console.log(b, c, valid, throwaway, fromBytes, fromKeypair, walletSigner, blockhash, sendInstructions);
```

`connection` takes a `CloakRpc`, `programId` and other addresses take Kit `Address` strings, and
`depositorKeypair` takes a `KeyPairSigner`. Wiring a browser wallet is covered in [Solana Kit
integration](/sdk/kit-integration).
