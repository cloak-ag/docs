`cloak-sdk` is a focused, engine-first Rust crate for building on Cloak. Its surface is the transact engine: you hand it a `TransactOptions`, it hands back a signed on-chain transaction (or submits it for you) along with the cached state to chain the next call.

Every flow the protocol supports — deposit, transfer, withdraw, swap — goes through one entrypoint:

```rust
pub async fn transact(opts: TransactOptions) -> Result<TransactResult>;
```

## What `transact()` does for you

Each call runs the full protocol pipeline end-to-end:

- SOL and SPL deposits, transfers, and withdrawals
- Swaps via `/transact_swap` with status polling
- Risk-oracle Ed25519 sigverify prepended at tx index 0
- Ephemeral ALT auto-creation for oversized v0 transactions
- Viewing-key challenge/register flow with process-local caching
- Chain-note v2 envelope (HKDF-SHA256 + AES-256-GCM)
- Stale-root retry loop with blockhash + transport backoff

The result carries the post-tx Merkle tree and any ALTs used — thread them into the next call to skip `/commitments` and ALT re-creation.

<Warning>
**The crate's compiled-in circuits base is stale.** `CIRCUITS_BASE_URL` in `cloak-sdk` still points at the `0.1.0` bundle. The deployed program embeds the `0.2.0` ceremony verifying key, so a proof built from `0.1.0` artifacts fails Groth16 verification and the transaction reverts with `0x1010` (`ProofInvalid`). The correct bundle base is `https://storage.googleapis.com/cloak-circuits/circuits/0.2.0`.

`TransactOptions` carries no circuits field and `transact()` resolves artifacts through the constant, so the base cannot be overridden per call. Until the crate is updated, seed the artifact cache once before your first `transact()`:

```rust
use cloak_sdk::utils::proof_generation::{default_cache_dir, ensure_circuit_artifacts_at};

ensure_circuit_artifacts_at(
    default_cache_dir()?,
    "https://storage.googleapis.com/cloak-circuits/circuits/0.2.0",
)
.await?;
```

`transact()` reuses whatever already exists in the cache directory, so it will not re-download the `0.1.0` artifacts.
</Warning>

<Warning>
Since the 2026-08-24 mainnet release the program only verifies proofs built from the `0.2.0` ceremony artifacts. If the crate revision you pin still has `CIRCUITS_BASE_URL` at `circuits/0.1.0`, pass the `0.2.0` base explicitly to `ensure_circuit_artifacts_at(cache_dir, base_url)` and clear any `0.1.0` cache — proofs from the old bundle fail on-chain.
</Warning>

## Install

```toml
[dependencies]
# cloak-sdk 0.1.0. Distributed by git only, and the repository publishes no
# tags, so a rev is the only way to pin. main has already moved once with a
# package rename and a full API rewrite, so do not track it unpinned.
cloak-sdk = { git = "https://github.com/cloak-ag/rustsdk", rev = "29b749d729f33d15e9bc7449b24783c94f5fb3a7" }
tokio = { version = "1", features = ["rt-multi-thread", "macros"] }
```

Runtime: the crate is async throughout and uses `tokio`.

## Minimal setup

```rust
use std::sync::Arc;

use cloak_sdk::{
    core::transact::{transact, TransactOptions},
    rpc::SolanaRpc,
};
use solana_keypair::Keypair;

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let rpc = Arc::new(SolanaRpc::new("https://api.mainnet-beta.solana.com"));
    let payer = Arc::new(Keypair::new());

    let opts = TransactOptions {
        rpc: Some(rpc),
        payer: Some(payer),
        relay_url: Some("https://api.cloak.ag".into()),
        // ...inputs / outputs / external_amount filled in per flow
        ..Default::default()
    };

    // Every output UTXO you put in `opts.outputs` must be cloned before it
    // moves in here, then stored with its leaf index from
    // `result.output_indices` before you use `result` for anything else.
    // See "Notes are yours to persist" below.
    let result = transact(opts).await?;
    println!("landed: {}", result.signature);
    Ok(())
}
```

`TransactOptions` is the single knob surface — no client builder, no stateful client object. Every flow is a different `TransactOptions` shape routed through the same `transact()` call.

## Notes are yours to persist

The engine has no wallet and no storage. `Utxo::new(amount, keypair, mint)` takes no blinding
argument: the per-note `blinding: Fr` it fills in is kept only inside the value it hands back,
and the chain stores nothing but the Poseidon commitment
`Poseidon(amount, public_key, blinding, mint_field)`. A note is spendable only by whoever
holds its `UtxoKeypair.private_key` together with its exact `blinding`, so a stored keypair
without its blinding is worth exactly what storing nothing is worth.

So, at every call site: clone each output `Utxo` before it moves into
`TransactOptions.outputs`, write `result.output_indices[i]` into the clone's `index`, and
store it before you touch the result for anything else. `Utxo` and `UtxoKeypair` both
derive `Clone`.

<Warning>
An output you constructed and then dropped is unspendable by you and by everyone else,
permanently. Nothing recovers it: the encrypted chain note carries an 8-byte timestamp,
not the blinding, so no scan of the chain can rebuild the note. On a transfer, a
withdrawal, or a swap the output that hurts is the **change**, because that is the balance
you kept.
</Warning>

Three details that bite:

- `result.output_indices[i]` is `Option<u32>` and reconciliation is best-effort, so `None`
  is a normal outcome. Store the note with `index: None` and backfill it later by matching
  `result.output_commitments[i]` against the tree. Never drop a note because its index is
  missing.
- `UtxoKeypair::from_spend_key(&[u8; 32])` is deterministic, so a keypair can be re-derived.
  The blinding cannot. Deriving keys does not remove the need to persist the note.
- The circuit takes 2 inputs, so spending three or more notes means merging them first, one
  `transact()` per round. Each round spends two notes on chain and creates one whose blinding
  exists only in memory, so store each round's output before starting the next. A sequence that
  dies halfway has already spent real notes. No user-level operation is exempt from this,
  including a withdrawal that empties the balance: the emptying call itself has nothing to
  store, but the rounds that fed it did. See
  [Errors and note persistence](/sdk/rust/error-handling#errors-and-note-persistence).

`cloak_sdk::storage::note_store::NoteStore` is the trait to implement for this
(`insert`, `mark_spent`, `unspent_for`, `all`), alongside
`cloak_sdk::storage::tree_cache::TreeCache` for the Merkle tree. The crate ships both
traits and no backend, so pick your own (sled, sqlite, Postgres). Treat the stored
`private_key` and `blinding` like wallet secrets and encrypt them at rest.

## Design at a glance

A few intentional choices shape how the crate reads:

- **Engine-first, no stateful façade.** The TS SDK ships optional stateful helpers such as `UtxoWallet` and `SimpleWallet` for local note tracking and input selection; the Rust crate exposes the engine directly and leaves that shape to you. Build your own wallet, scanner, or compliance report on top — `TransactResult` gives you the commitments, indices, and post-tx tree to do it. The flip side is that [note persistence is entirely yours](#notes-are-yours-to-persist), and an output you fail to store is money nobody can spend.

<Warning>
Treat those two TS helpers as a sketch of the shape, not a specification to port. `UtxoWallet.prepareSend` ignores its recipient argument and builds the recipient's note under a freshly generated random keypair, and it hardcodes the native SOL mint on both the recipient note and the change, so the recipient cannot spend what they were sent and a non-SOL send is built against the wrong mint. `SimpleWallet.send` delegates to it and inherits both. The TS `transfer` helper has the mirror-image property, correctly: it builds the recipient output with `privateKey === 0n` because the sender does not hold the recipient's key, which means a sender must never count that output into their own balance. Whatever you build in Rust, the recipient's `UtxoKeypair.public_key` has to come from the recipient, and only outputs you can actually spend belong in your balance.
</Warning>
- **`TransactOptions` as the one knob.** Parameters (inputs, outputs, external_amount, recipient) and submission config (rpc, payer, relay_url, risk checks) live on one struct. `..Default::default()` + struct-update syntax keeps call sites readable.
- **`RpcProvider` is a trait.** Production wraps `solana-rpc-client::nonblocking::RpcClient` via `SolanaRpc`; tests inject `MockRpc`. Same shape, no cfg-gated code paths.
- **Focused Solana crates.** Depends on `solana-keypair`, `solana-pubkey`, `solana-transaction`, `solana-rpc-client`, etc. — not the `solana-sdk` umbrella. Keeps the dep graph predictable and compile times reasonable.
- **Typed retry classification.** `Error::RootNotFound` / `Error::StaleProofState` / `Error::BlockhashExpired` are variants the retry loop matches on directly — no string-sniffing, no `Box<dyn Error>` hand-unwrapping.
