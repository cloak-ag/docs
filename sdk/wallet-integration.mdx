## Install

```bash
npm install @cloak.dev/sdk@0.2.6 @solana/kit @solana/wallet-adapter-react @solana/web3.js
```

The SDK is built on `@solana/kit`. `@solana/web3.js` is still needed here because the wallet-adapter
bridge hands the wallet a `VersionedTransaction` to sign — see [Solana Kit
integration](/sdk/kit-integration).

Add wallet UI packages as needed:

```bash
npm install @solana/wallet-adapter-react-ui @solana/wallet-adapter-wallets
```

## The two wallet callbacks, and what each one is for

A browser integration needs both, and they do different jobs:

| Option | Signs | Needed for |
|---|---|---|
| `signTransaction` | the Solana transaction | **deposits**, which the wallet submits directly |
| `signMessage` | the request preimage | **private sends, withdrawals and swaps**, which are submitted for you |

`signMessage` also covers viewing-key registration, but that is the smaller half of its job. Without
it, a deposit still succeeds and every send afterwards is refused. Full contract, including the
approval window and prompt counts: [Request authentication](/sdk/request-authentication).

## UTXO integration with wallet signing

For UTXO `transact` deposits in browser apps, pass wallet signing fields in `TransactOptions`:

```typescript
import { serializeUtxo, transact } from "@cloak.dev/sdk";

const result = await transact(params, {
  connection,
  programId,
  relayUrl,
  signTransaction, // wallet adapter signer, for the deposit transaction
  signMessage, // wallet adapter message signer, authenticates submitted requests
  depositorPublicKey, // wallet public key
  walletPublicKey: depositorPublicKey, // same key; becomes the authenticated sender
  ownerUtxoKeypair, // the wallet's long-lived UTXO keypair; owns its notes and supplies nk
  riskOracleQueue, // if required by deployment
  riskQuoteUrl, // absolute URL on this build's allowlist (if needed)
  addressLookupTableAccounts,
});

// `result.outputUtxos` is the money this deposit created, and the SDK stores none of it.
// Write the bytes down before you report success. Zero-amount outputs are circuit
// padding, so drop them. `persistNotes` is your own storage, not the SDK's: it has
// none, and it must have committed before it resolves.
// See "Where your notes live between sessions" below.
await persistNotes(
  result.outputUtxos.filter((utxo) => utxo.amount > 0n).map(serializeUtxo),
);
```

Check `signMessage` is present before you offer a send or withdraw action. Not every adapter
implements it, and finding out after a Groth16 proof has already been computed is a poor experience.

### The wallet's two keys

Derive both from the wallet's spend key once, and pass them on every flow:

```typescript
import { deriveUtxoKeypairFromSpendKey, getNkFromUtxoPrivateKey } from "@cloak.dev/sdk";

const ownerUtxoKeypair = await deriveUtxoKeypairFromSpendKey(skSpend); // owns and spends notes
const nk = getNkFromUtxoPrivateKey(ownerUtxoKeypair.privateKey);       // finds and reads notes
```

`ownerUtxoKeypair` owns every note the wallet creates for itself (deposits, change, merges, swap
refunds), and it is required by `transfer`, `partialWithdraw`, `fullWithdraw`, `swapUtxo` and
`swapWithChange`. **`nk` is view-only: it can find and read your notes, never spend them or sign for
funds.** It is the value registered as your viewing key and the value you can share with someone who
should see your history. When you pass `ownerUtxoKeypair` without `chainNoteViewingKeyNk`, the SDK
uses this canonical `nk`. The SDK never infers `nk` from a note's own key, so a flow with neither
throws before touching the network.

<Note>
`ownerUtxoKeypair`, `SpendOptions` and the options-object form of `createRecoverableDepositUtxo`
are 0.2.6 signatures. Code written for 0.2.5 throws on 0.2.6 until it passes them.
</Note>

## Full wallet-adapter SOL send flow (`transact` -> `fullWithdraw`)

```typescript
import {
  CLOAK_PRODUCTION_RELAY_URL,
  CLOAK_PROGRAM_ID,
  NATIVE_SOL_MINT,
  createRecoverableDepositUtxo,
  createZeroUtxo,
  fullWithdraw,
  isRootNotFoundError,
  serializeUtxo,
  address,
  createCloakRpc,
  transact,
  type Address,
  type UtxoKeypair,
} from "@cloak.dev/sdk";

// Your own durable store. The SDK ships nothing that plays this role.
declare function saveNoteBytes(bytes: Uint8Array): Promise<void>;

const connection = createCloakRpc(process.env.SOLANA_RPC_URL!);
const relayUrl = CLOAK_PRODUCTION_RELAY_URL;
const programId = CLOAK_PROGRAM_ID;

async function sendWithWalletAdapter({
  walletPublicKey,
  signTransaction,
  signMessage,
  ownerUtxoKeypair,
  nk,
  recipientAddress,
  amountLamports,
}: {
  // A Kit Address. From a wallet adapter: addressFromPublicKey(wallet.publicKey).
  walletPublicKey: Address;
  signTransaction: (tx: any) => Promise<any>;
  signMessage: (msg: Uint8Array) => Promise<Uint8Array>;
  // The wallet's two keys, derived once from its spend key (see "The wallet's two keys").
  ownerUtxoKeypair: UtxoKeypair;
  nk: Uint8Array;
  recipientAddress: string;
  amountLamports: bigint;
}) {
  // Owned by the wallet keypair; only the blinding comes from nk and the salt.
  const { utxo: output, noteSalt } = await createRecoverableDepositUtxo({
    amount: amountLamports,
    viewingKeyNk: nk,
    ownerUtxoKeypair,
    mintAddress: NATIVE_SOL_MINT,
  });

  const deposited = await transact(
    {
      inputUtxos: [await createZeroUtxo(NATIVE_SOL_MINT)],
      outputUtxos: [output],
      externalAmount: amountLamports,
      depositor: walletPublicKey,
    },
    {
      connection,
      programId,
      relayUrl,
      signTransaction,
      signMessage,
      depositorPublicKey: walletPublicKey,
      walletPublicKey,
      chainNoteViewingKeyNk: nk,
      chainNoteSalt: noteSalt,
      ownerUtxoKeypair,
      onProgress: (status) => console.log("deposit", status),
      onProofProgress: (percent) => console.log("deposit proof", percent),
    },
  );

  // Persist before the withdrawal. The retry loop below can prompt the wallet three
  // times, and a tab closed at any of them leaves this note as the only claim on the
  // deposited funds. `saveNoteBytes` is your own storage, not an SDK export.
  await saveNoteBytes(serializeUtxo(deposited.outputUtxos[0]));

  const recipient = address(recipientAddress);
  let withdrawResult: Awaited<ReturnType<typeof fullWithdraw>> | undefined;

  for (let attempt = 1; attempt <= 3; attempt += 1) {
    try {
      withdrawResult = await fullWithdraw(deposited.outputUtxos, recipient, {
        connection,
        programId,
        relayUrl,
        walletPublicKey,
        signMessage,
        chainNoteViewingKeyNk: nk,
        ownerUtxoKeypair, // required on every spend flow
        cachedMerkleTree: deposited.merkleTree,
        onProgress: (status) => console.log("withdraw", status),
        onProofProgress: (percent) => console.log("withdraw proof", percent),
      });
      break;
    } catch (error) {
      if (!isRootNotFoundError(error) || attempt === 3) throw error;
      await new Promise((resolve) => setTimeout(resolve, 1_500));
    }
  }

  if (!withdrawResult) throw new Error("withdraw did not produce a result");

  return {
    depositSignature: deposited.signature,
    withdrawSignature: withdrawResult.signature,
  };
}
```

Notes:

- `relayUrl` comes from the exported `CLOAK_PRODUCTION_RELAY_URL`, not from an environment read.
  The SDK reads no environment variable for the submission endpoint, so exporting `CLOAK_RELAY_URL`
  does nothing on its own; if you want the value configurable, read your own build-time variable in
  your app and pass the result as `relayUrl`. Whatever you pass still has to be an origin on this
  build's allowlist. On the default path, where `enforceViewingKeyRegistration` stays on, omitting
  `relayUrl` or passing `""` throws `Viewing key registration is mandatory: relayUrl is required.`
  before anything reaches the network, deposits included. See
  [which endpoint the SDK talks to](/sdk/request-authentication#which-endpoint-the-sdk-talks-to-and-which-rpc-you-use).
- Keep amount values as `bigint` end-to-end.
- Use `cachedMerkleTree` from deposit for the immediate withdraw call.
- Treat `isRootNotFoundError` as retryable with bounded backoff.
- This example spends `deposited.outputUtxos` in the same breath as producing them, which is what
  makes it short. A real wallet has to persist them instead: see
  [where your notes live between sessions](#where-your-notes-live-between-sessions).
- The withdrawal here spends **two** notes at most, so no consolidation round runs and the retry
  loop is safe to write this way. Handing `fullWithdraw` three or more notes is a different call
  with a different failure mode: see
  [a withdrawal of three or more notes is not exempt](#a-withdrawal-of-three-or-more-notes-is-not-exempt).

## Where your notes live between sessions

Every example above ends by feeding `deposited.outputUtxos` straight into the next call. A real
wallet cannot do that. The user closes the tab, comes back tomorrow, and something has to know what
they own.

The SDK does not persist anything for you. `transact`, `transfer`, `partialWithdraw`, `fullWithdraw`
and the swap helpers each return their new notes on `result.outputUtxos` and then forget them. That
storage boundary is explicit, and closing it is your job.

`fullWithdraw` leaves nothing shielded, so it hands back no change note **when it spends one or two
notes**. That is the whole of its exemption, and the next section is why. Every other call in
that list produces a change note on every path. `swapUtxo` and `swapWithChange` additionally return
`refund` and `swapStatePda` on `UtxoSwapResult`, which is what reclaims the principal if the swap
times out before it settles; persist those two alongside the notes.

<Warning>
Write `result.outputUtxos` to durable storage before you report success to the user. A note is
spendable only with its full secrets, `(amount, owner pubkey, blinding, mint)`, plus the owner's
private key. The SDK derives the `blinding` of deposits and change from your `nk` and a salt the
chain note carries, so a scan can rebuild some of them (see
[what happens if that storage is lost](#what-happens-if-that-storage-is-lost)), but not all: a
`transfer`'s change and consolidation merges are not surfaced by any scan, and a note built with
`createUtxo` has a random blinding that is published nowhere. Treat recovery as a repair tool, not as
storage.
</Warning>

### A withdrawal of three or more notes is not exempt

The circuit takes two inputs. `partialWithdraw`, and therefore `fullWithdraw`, which is a thin
wrapper that calls `partialWithdraw` for the whole input sum, absorbs a larger set by **merging on
chain first**: while more than two notes remain it spends the two smallest in a shield-to-shield
`transact` and creates one merged note in their place, repeating until two are left, and only then
builds the withdrawal itself. For `n` input notes that is `n - 2` settled merges ahead of the
withdrawal.

Each round is a real transaction. It nullifies two of your notes on chain and publishes the merged
commitment, owned by `ownerUtxoKeypair`, living in a local variable inside a call that has not
returned yet. You are never handed it, because the merge is an implementation detail of the
withdrawal.

<Warning>
**If a withdrawal of three or more notes throws part way through, you are not handed the merged
note.** The consumed inputs are spent and the merged note sits on chain. There is nothing to
persist, because the call produced no result at all. Exhausted stale-root retries, a rejected wallet
prompt, a failed submission or a closed tab all reach that state. The merged note's blinding is
derived from your `nk` and the salt in that merge's chain note, but `scanTransactions` does not
surface merge outputs, so your app has no ready-made path back to it. See
[what happens if that storage is lost](#what-happens-if-that-storage-is-lost).
</Warning>

You avoid that window rather than recover from it. Keep withdrawal inputs at two notes or fewer, and
when they are not, merge deliberately: build the merged output yourself so you hold its secrets
before anything is submitted.

```typescript
import {
  createRecoverableChangeUtxo,
  randomChangeNoteSalt,
  serializeUtxo,
  transact,
  type SpendOptions,
  type Utxo,
} from "@cloak.dev/sdk";

// One deliberate merge round, in place of one round the withdrawal would have run
// for you. The difference is that the secret exists in your storage first.
async function mergeTwo(a: Utxo, b: Utxo, nk: Uint8Array, options: SpendOptions) {
  // The merged note is owned by the wallet keypair, never by an input's own key, and
  // its blinding is anchored to a fresh salt that must reach the chain note.
  const salt = randomChangeNoteSalt();
  const { utxo: merged } = await createRecoverableChangeUtxo(
    a.amount + b.amount, options.ownerUtxoKeypair, nk, a.mintAddress, salt, 0,
  );

  // Write it down before submitting. Only `index` is still missing at this point,
  // and `index` is recoverable from chain state.
  await persistNotes([serializeUtxo(merged)]);

  const result = await transact(
    { inputUtxos: [a, b], outputUtxos: [merged], externalAmount: 0n },
    { ...options, chainNoteViewingKeyNk: nk, chainNoteSalt: salt },
  );

  // On success, replace the provisional copy with the one carrying the leaf index.
  await persistNotes(
    result.outputUtxos.filter((utxo) => utxo.amount > 0n).map(serializeUtxo),
  );
  return result;
}
```

<Note>
`onProgress` is the only signal a caller gets that consolidation is happening at all. It fires
`Consolidating notes (n remaining)...` once per round. A withdrawal that emits that string is inside
the window above until it resolves, so treat it as a state worth surfacing rather than a spinner
label.
</Note>

### The two storage exports, and how they relate

| Export | Holds | Persists itself |
|---|---|---|
| `UtxoWallet` | the live `Utxo` set per mint, spent flags, balance, input selection | No. `serialize()` and the static `UtxoWallet.deserialize()` hand you a JSON string; where it goes is your choice |
| `LocalStorageAdapter`, `MemoryStorageAdapter` (both implement `StorageAdapter`) | `CloakNote` records, plus wallet key material through `saveKeys` / `loadKeys` | `LocalStorageAdapter` writes to browser `localStorage`, keys `cloak_notes` and `cloak_wallet_keys` by default; `MemoryStorageAdapter` keeps everything in process and loses it on reload |

`UtxoWallet` does not accept a `StorageAdapter`, and a `StorageAdapter` does not store `Utxo`
objects. They cover different halves of the problem: `UtxoWallet` is the spendable note set, the
adapters are a ready-made place to keep key material. The note set is the half that decides
solvency.

For a single note rather than a whole set, `serializeUtxo(utxo)` returns a `Uint8Array` and
`deserializeUtxo(bytes)` returns a `Promise<Utxo>`. Those are the primitives if you keep notes in
your own table or send one across a boundary; `UtxoWallet.serialize()` is the batch form.

### A note set that survives a reload

```typescript
import {
  LocalStorageAdapter,
  UtxoWallet,
  type CloakKeyPair,
} from "@cloak.dev/sdk";

const NOTES_KEY = "myapp.cloak.notes";
const storage = new LocalStorageAdapter();

function loadWallet(): UtxoWallet {
  const saved = window.localStorage.getItem(NOTES_KEY);
  return saved ? UtxoWallet.deserialize(saved) : new UtxoWallet();
}

function saveWallet(wallet: UtxoWallet): void {
  window.localStorage.setItem(NOTES_KEY, wallet.serialize());
}

// Key material has a ready-made home on the adapter.
async function loadKeys(): Promise<CloakKeyPair | null> {
  return await storage.loadKeys();
}
```

`serialize()` writes the bigints out as strings, so a plain `JSON.stringify` over raw `Utxo` objects
is not a substitute; it throws on `bigint`. Use `serialize()` / `deserialize()` as the pair.

Then record the result of every flow, in the same tick that the flow returns:

```typescript
import { transact } from "@cloak.dev/sdk";

const wallet = loadWallet();

const result = await transact(params, options);

for (const utxo of result.outputUtxos) {
  wallet.addUtxo(utxo, utxo.mintAddress);
}
saveWallet(wallet); // before any "done" is shown

// On a spend, the inputs stop being yours.
for (const spent of inputUtxos) {
  wallet.markSpent(spent, spent.mintAddress);
}
for (const utxo of result.outputUtxos) {
  wallet.addUtxo(utxo, utxo.mintAddress);
}
saveWallet(wallet);
```

<Note>
`serialize()` carries amount, keypair, blinding, leaf `index` and the spent flag. It does not carry
`commitment`, so notes coming back out of `deserialize()` have `commitment` undefined, and
`verifyUtxos` reports every one of them as `skipped` rather than spent or unspent. Recompute before
you reconcile against chain state:

```typescript
import { computeUtxoCommitment, NATIVE_SOL_MINT } from "@cloak.dev/sdk";

for (const utxo of wallet.getUnspentUtxos(NATIVE_SOL_MINT)) {
  if (utxo.commitment === undefined) {
    utxo.commitment = await computeUtxoCommitment(utxo);
  }
}
```
</Note>

### How `selectUtxos` consumes what storage returns

`selectUtxos(available, targetAmount)` is a pure function over an array you supply. `available` is
exactly what your store hands back: the unspent notes for one mint.

```typescript
import { NATIVE_SOL_MINT, selectUtxos, transfer } from "@cloak.dev/sdk";

const available = wallet.getUnspentUtxos(NATIVE_SOL_MINT); // WalletUtxo[], extends Utxo
const selected = selectUtxos(available, 30_000_000n);

if (!selected) throw new Error("insufficient shielded balance");
if (selected.length > 2) throw new Error("consolidate before sending");

// `walletOptions` is SpendOptions: it must carry `ownerUtxoKeypair`, which owns the change.
const sent = await transfer(selected, recipientUtxoPublicKey, 30_000_000n, walletOptions);

// The inputs are spent and your change is in `sent.outputUtxos`. Record both, and save,
// before you report the send as done.
for (const spent of selected) {
  wallet.markSpent(spent, spent.mintAddress);
}
for (const utxo of sent.outputUtxos) {
  wallet.addUtxo(utxo, utxo.mintAddress);
}
saveWallet(wallet);
```

Two things it does not do:

- It returns `null` when the balance is short, rather than throwing. A truthy check is the whole
  error path.
- It does not know about the circuit's two-input limit. It will happily return three notes, and
  `transact` then throws `Maximum 2 input UTXOs allowed` before proving. `transfer` does not
  consolidate, so cap the selection yourself. `partialWithdraw` and `fullWithdraw` do consolidate,
  merging the two smallest notes repeatedly until two remain, and that convenience is the one
  described in
  [a withdrawal of three or more notes is not exempt](#a-withdrawal-of-three-or-more-notes-is-not-exempt):
  it settles merges whose secrets you never receive, so cap the selection before a withdrawal too
  and run the merges yourself.

`UtxoWallet.selectInputs(amount, mint, strategy)` does the same job against the wallet's own
bookkeeping and throws instead of returning `null`.

<Warning>
Do not build sends with `UtxoWallet.prepareSend` or `SimpleWallet`. `prepareSend` creates the
recipient output from a freshly generated random keypair rather than from the recipient's key, so
the recipient cannot spend what it produces, and `SimpleWallet.sync()` throws
`Sync not yet implemented`. Use `transfer`, which derives the recipient output from the Cloak pubkey
you pass it. `UtxoWallet` is sound for the parts used above: `addUtxo`, `markSpent`, `getBalance`,
`getUnspentUtxos`, `getStats`, `selectInputs`, `serialize` and `deserialize`.
</Warning>

### What happens if that storage is lost

Most of it does not come back. Be precise with yourself about which parts do. The table describes a
`scanTransactions` chain scan. From 0.2.6, restore with `recoverNotesFromIndex` instead: it finds
the same notes with one RPC request rather than a walk over every transaction, and it also restores a
`transfer`'s change, by conservation over the wallet's own inputs to that send. See
[Restore notes from the Note Index](/sdk/note-index).

| What was lost | Recoverable from chain | Why |
|---|---|---|
| Change from `partialWithdraw` or `swapWithChange` | Yes, with `nk` plus your UTXO public key | The change is output 0 and owned by `ownerUtxoKeypair`; its blinding is derived from `nk` and the salt the chain note carries, and the chain note describes output 0. It comes back on `recoveredChangeNotes` |
| Change from a `transfer` | **No** | The blinding is derivable, but the change is output 1 and the chain note describes output 0 only, so no scan learns its amount. A sender who knows what they sent can rebuild it |
| A consolidation merge | **No ready-made path** | Its blinding is derivable, but no scan surfaces merge outputs |
| A deposit built with `createUtxo` | **No** | Its `blinding` is random and written nowhere. It appears in history as an amount, which is not a spendable note |
| A deposit built with `createRecoverableDepositUtxo` | Yes, with `nk` plus your UTXO public key | The note is owned by `ownerUtxoKeypair` and its blinding is derived from `nk` and the salt the chain note carries. It comes back on `recoveredDepositNotes` |
| A note someone sent you, when the sender passed `recipientViewingPublicKey` | Yes | The sender sealed `amount` and `blinding` into an on-chain envelope addressed to your viewing key |
| A swap input stranded by a timeout | Yes, if the refund was derived | `discoverSwapRefunds(connection, programId, nk, { ownerUtxoKeypair })` replays the blinding over refund leaves. Swaps whose refund was drawn from raw randomness exist only in the `refund` field of the `UtxoSwapResult` you were handed |

In every "Yes" row the scan finds the note with key material that cannot spend it. Recovered current
notes come back with `keypair.privateKey === 0n`; substitute the wallet's own `ownerUtxoKeypair`
before spending.

**`scanTransactions` is not note recovery.** It decrypts your own chain notes with `nk` and produces
the history rows the site documents elsewhere: gross, fee, `netAmount` and a running balance, ready
for `toComplianceReport`. Two of its fields are the deliberate exception and are kept out of
`transactions` and `summary` precisely because they are secrets rather than history:
`deliveredNotes` (inbound notes whose sender opted in), and `recoveredDepositNotes` and
`recoveredChangeNotes` (your own deposits and withdrawal or swap change, built recoverably). Everything else it returns tells you a deposit of
0.02 SOL happened. It does not give you something you can spend.

The reason sits in the chain note. Every transaction posts one, sealed under the writer's own
viewing key, and its plaintext is `{ timestamp, noteSalt, outAmount0, outPubkey0, isSendToSelfKey0 }`:
the output note's amount and owner pubkey, and no `blinding`. A chain note
alone therefore cannot rebuild a spendable note, which is the whole reason the recoverable-deposit
shape exists. See
[the on-chain chain note is not a delivery channel](/sdk/shielded-transfers#the-on-chain-chain-note-is-not-a-delivery-channel).

`scanRecipientDeliveryNotes` recovers only notes sent **to** you by a sender who passed
`recipientViewingPublicKey`. It never surfaces your own change, and it surfaces nothing at all when
the sender omitted that option.

An empty scan is not proof that nothing is stranded. It means nothing in the scanned window was
derivable from this `nk` and UTXO public key.

### Making deposits recoverable

If you want a deposit that a scan can rebuild later, build the output note with
`createRecoverableDepositUtxo` and hand the same salt to `transact`:

```typescript
import { createRecoverableDepositUtxo, createZeroUtxo, NATIVE_SOL_MINT, transact } from "@cloak.dev/sdk";

const { utxo, noteSalt } = await createRecoverableDepositUtxo({
  amount: 20_000_000n,
  viewingKeyNk: nk,
  ownerUtxoKeypair,
  mintAddress: NATIVE_SOL_MINT,
});

const deposit = await transact(
  { inputUtxos: [await createZeroUtxo(NATIVE_SOL_MINT)], outputUtxos: [utxo], externalAmount: 20_000_000n },
  { ...options, chainNoteViewingKeyNk: nk, chainNoteSalt: noteSalt, ownerUtxoKeypair },
);

// Recoverable is the fallback, not the plan. `deposit.outputUtxos` comes back with the leaf
// index already filled in, so persist it now and keep the scan as a repair tool.
for (const out of deposit.outputUtxos) {
  wallet.addUtxo(out, out.mintAddress);
}
saveWallet(wallet);
```

The note is owned by `ownerUtxoKeypair`; only its blinding comes from `(nk, noteSalt)`. The salt has
to reach the chain note, which is what `chainNoteSalt` does, and `transact` refuses a `chainNoteSalt`
without the wallet's `nk` (explicit, or the canonical `nk` of `ownerUtxoKeypair`).

To find it again, scan with the wallet's `nk` and its UTXO public key:

```typescript
import { scanTransactions } from "@cloak.dev/sdk";

const scan = await scanTransactions({
  connection,
  programId,
  viewingKeyNk: nk,
  ownerUtxoPublicKey: ownerUtxoKeypair.publicKey, // public; the scan stays view-only
});

for (const note of [...scan.recoveredDepositNotes, ...scan.recoveredChangeNotes]) {
  // Current notes: privateKey is 0n, because nk cannot produce it. Spend with your own keypair.
  const keypair = note.legacyExposed ? note.keypair : ownerUtxoKeypair;
  // ...rebuild { amount, blinding, keypair, mintAddress, commitment }, look up the leaf index,
  // then run verifyUtxos before treating it as spendable.
}
```

Recovered notes are authenticated by recomputing a commitment the transaction actually published.
Without `ownerUtxoPublicKey` the scan can still decrypt your chain notes, but it cannot match a
current deposit, because the note's owner is not derivable from `nk`.

Notes flagged `legacyExposed` were built by an earlier SDK release whose note key was derived from
`nk`. They come back complete and spendable. Move them under the wallet keypair at the first
opportunity by spending them to yourself (for example `transfer(notes, ownerUtxoKeypair.publicKey,
amount, options)`), and treat the result as an ordinary note.

Pick one key pair per wallet and use it everywhere: `ownerUtxoKeypair =
deriveUtxoKeypairFromSpendKey(skSpend)`, and `nk = getNkFromUtxoPrivateKey(ownerUtxoKeypair.privateKey)`
at deposit time (`chainNoteViewingKeyNk`) and at scan time (`viewingKeyNk`). Deriving both from the
spend key makes them reproducible, so the keys need never be the thing you lose. The note set still
has to be written down.

<Note>
Two devices sharing one note set will each believe a spent note is unspent, and the second spend
fails with `DoubleSpend` (`0x1020`). `verifyUtxos(utxos, connection, programId)` partitions your
local notes into `spent`, `unspent` and `skipped` in a single batched RPC call; run it on load and
after any failure, and drop anything it reports as spent.
</Note>

## UX requirements

- Persist `result.outputUtxos` before you report a flow as successful. A lost change note is
  unspendable value, not a resyncable cache.
- Pass `ownerUtxoKeypair` on every spend flow, and keep it out of anything you share. Share `nk`
  only with someone who should see your history: it can find and read notes, never spend them.
- When a scan returns notes flagged `legacyExposed`, offer the user a one-step move of those funds
  into a note owned by the wallet keypair.
- Cap withdrawal inputs at two notes, and merge deliberately above that. A withdrawal handed three
  or more notes consolidates on chain first, and a failure part way through loses the merged value
  outright, with no result to persist.
- Show progress during proof generation (`onProgress`, `onProofProgress`).
- Handle stale-root retries gracefully (`isRootNotFoundError`).
- Keep circuit files accessible in browser deployments.
- Ensure viewing-key registration succeeds before transact/swap actions.
- For privacy history pages, expose explicit cache clear + rescan controls after swaps or failed scans.
